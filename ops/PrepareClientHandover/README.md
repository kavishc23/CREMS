# Client handover preparation

Adds fictional rental walkthrough records to an **existing active customer account** in the local `Crems` SQL database. Credentials are never written to this utility. Connection configuration uses the API's existing user secrets or environment.

From the repository root:

```sh
./.dotnet/dotnet run --project ops/PrepareClientHandover -- --customer-email customer@example.com
./.dotnet/dotnet run --project ops/PrepareClientHandover -- --customer-email customer@example.com --apply
./.dotnet/dotnet run --project ops/PrepareClientHandover -- --customer-email customer@example.com --verify
```

The first command previews only. `--apply` adds eight assets per active category across public branches, plus dedicated assets and linked records for 48 primary scenarios. It creates a separate next reservation for the extension-conflict scenario. All records use the Fiji local date when run. Active categories/services, configured inspection checklists, fees, VAT and approval stages are reused. Existing customer records, credentials, preferences and licences are preserved.

Cases include quotation preparation, acceptance, decline, revision, expiry, approval, pickup, prepaid and partial payment, existing damage, replacement, maintenance/safety blocks, required documents, returns, fuel and usage charges, bond refunds/retention, extensions and conflicts, cancellation, incidents, incident closure, disputed settlement, paid/unpaid invoices, credits, delivery and personnel-supported hire.

No emails or automatic notifications are generated by this utility. Seeded receipts, agreements, incident descriptions and audit entries explicitly identify fictional preparation data. The signature fixture reads **SAMPLE HANDOVER RECORD / Not a customer signature**. The attached sample Event Approval is not an approval issued by an authority. Catalogue photographs are representative category/model illustrations reused from the bundled catalogue; they are not evidence of a particular physical unit's condition.

The `HO` reference range and the scenario notes identify the preparation dataset. Reapplying for the same customer and Fiji date preserves the prepared cases rather than resetting completed walkthrough actions or creating another fleet. If the current date's reference range belongs to a different customer, the command must be run for that original account. It does not delete data. Invalid input, unauthorized access, stale-version and duplicate-action exceptions are demonstrated against valid seeded records, rather than saved as corrupt database rows. Customer-wide restrictions should be explained or tried with a separate account, not by blocking the handover customer.

All active assets are checked for local photos. Missing/broken references are replaced using the appropriate bundled image and copied to `App_Data/asset-images/<asset-id>/seed-<file>`. Existing readable uploaded pictures remain attached. Original photo metadata is backed up under `output/client-handover`. The public asset-photo API serves these files to both portals. Copy the database **and** `App_Data` when moving this prepared dataset to another computer; Git alone does not transfer local database content or runtime uploads.

Generated scenario manifests, integrity results and photo manifests are written to `output/client-handover`. These include current amounts and references; no passwords are included. `--verify` checks photo files, ownership, dates, rates, invoice balances and pickup-readiness reasons without modifying rental records. It is a data check, not an exhaustive end-to-end application test.
